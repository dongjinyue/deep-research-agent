# 验证驱动开发（Verification-driven Development）

## 一句话理解

验证驱动开发（Verification-driven Development）是在实现前就明确“用什么证据证明功能正确”，再让规格、验收、验证和实现形成闭环。

```text
规格
  ↓
验收标准
  ↓
验证方法
  ↓
证据
  ↓
完成
```

完成不是 AI 的主观判断，而是证据支持的结论。

## Claim ≠ Evidence

Claim（声明）不等于 Evidence（证据）。

> “已修复”“已测试”“全部通过”只是声明；可复现的测试结果、构建结果、界面行为和可审查的 Diff（差异）才是证据。

收到 AI 的完成总结后，应继续问：

- 哪条规格被验证？
- 哪个用例证明了它？
- 命令是否真的运行，结果是什么？
- 测试没有覆盖什么？
- Diff 是否包含范围外修改？

## 可追溯链

Traceability（可追溯性）是从一条规格一路定位到完成证据的能力。

本项目的例子：

```text
规格：Task 进入 cancelled 或 failed 后不再执行 Steps
  ↓
验收标准：执行期终止后 Plan 与 Step 状态冻结，不再注册推进计时器
  ↓
验证方法：fake timers 推进到终态，再额外推进 3 秒
  ↓
证据：Task 仍在终态、Step 状态未变、计时器数量为 0
  ↓
完成：该规则有直接证据支持
```

链条任一环缺失，都不能把“看起来实现了”当作“已证明完成”。

## Verification Matrix 与 Verification Gap

Verification Matrix（验证矩阵）把规格、验收标准、验证方法和证据放在同一张表中，便于发现遗漏。

| 规格规则 | 可观察验收标准 | 验证方法 | 当前证据 |
| --- | --- | --- | --- |
| Steps 串行执行 | 任一时刻最多一个 `running` | 领域测试逐步推进并统计 `running` | 每个中间状态都恰有一个 `running` |
| 全部 Steps 完成后生成报告 | 最后一步后 Task 进入 `generating` | 虚拟时间逐段断言 | 状态序列到达 `generating`，Steps 全为 `completed` |
| 执行期终态停止推进 | `failed`／`cancelled` 后状态冻结 | 进入终态后继续推进虚拟时间 | Task 与 Steps 不变，计时器为 0 |
| 旧回调不能污染新 Task | 新提交 Task 只由自己的计时器推进 | 在旧计时器未触发时提交第二个 Task | 旧计时器到点时第二个 Task 仍为 `planning` |
| 当前切片只做本地 Mock | 生命周期无网络和持久化副作用 | 监视 `fetch`、XHR、Storage、IndexedDB | 生命周期完成且这些入口未被调用 |

Verification Gap（验证缺口）是“已经要求，但没有足够证据”的部分。常见缺口包括：

- 验收标准没有对应测试或人工检查。
- 测试只执行了代码，却没有断言关键结果。
- 只测最终状态，没有测中间顺序和不变量。
- 只测正常路径，没有测失败、取消和清理。
- 测试通过，但没有检查生产构建、真实界面或 Diff。

## 四层验证及其边界

| 验证层 | 主要证明什么 | 不能证明什么 |
| --- | --- | --- |
| Static Verification（静态验证） | 类型、语法、接口使用和部分非法状态在运行前可被发现 | 不能证明运行时状态顺序、界面可用或业务规则正确 |
| Automated Tests（自动化测试） | 已编写用例覆盖的输入、状态转换和用户可观察行为可重复通过 | 不能证明未覆盖场景、测试断言本身正确或规格没有遗漏 |
| Build Verification（构建验证） | 生产配置能够完成编译和打包，入口与依赖可解析 | 不能证明打包后的交互正确、边界行为完整或用户体验良好 |
| Manual Verification（人工验证） | 真实界面、交互、文案、控制台和整体体验符合预期 | 不能稳定穷举所有路径，也不能替代可重复的回归测试 |

四层是互补关系，不是互相替代。纯文档改动可以按项目规则缩小验证范围，但仍要检查内容、链接、Diff 和范围。

## 行为测试 vs 实现细节测试

Behavior Test（行为测试）验证外部可观察结果和领域契约；Implementation-detail Test（实现细节测试）固定内部写法。

更稳定的行为断言：

- 提交有效问题后页面显示 `planning`，此时没有 Plan。
- 每次推进后 Step 状态按顺序变化，最多一个 `running`。
- 进入终态后继续推进时间，状态保持不变。
- 页面不展示百分比，也不调用真实研究服务。

脆弱的实现细节断言：

- 某个私有函数恰好被调用一次。
- 必须使用某个局部变量名或组件内部结构。
- 只做大范围快照，却不说明关键业务结果。

实现可以重构，行为契约应保持稳定。只有当内部边界本身就是明确契约时，才值得直接测试实现结构。

## Happy Path 与 Failure Path

Happy Path（正常路径）证明理想条件下的主流程：

```text
planning
→ researching：running, pending, pending
→ researching：completed, running, pending
→ researching：completed, completed, running
→ generating：completed, completed, completed
→ completed
```

Failure Path（失败路径）验证系统在失败、取消、非法输入和清理场景下仍保持规则。本项目至少包括：

- `planning` 期间失败或取消：不生成 Plan，不启动正常推进。
- `researching` 期间失败或取消：保留 Plan，冻结现有 Step 状态，不再推进。
- 非法状态转换：抛出错误，不能绕过状态机。
- 空问题或只含本地 Mock 标记：不能创建 Task。
- 新 Task 替换旧 Task：旧异步回调不能推进新 Task。

只验证 Happy Path，会把最容易在真实使用中暴露的问题留给用户。

## Invariant：跨全过程都必须成立的规则

Invariant（不变量）不是某个时刻的期望值，而是在所有合法路径和时间点都必须成立的约束。

当前 `ResearchTask`／`ResearchStep` 的关键不变量：

1. 同一时间最多一个 Research Step 为 `running`。
2. Steps 只能按计划顺序从 `pending → running → completed` 推进。
3. Task 进入 `generating` 前，全部 Steps 必须为 `completed`。
4. `completed`、`failed`、`cancelled` 是终态，不能再次转换或自动推进。
5. Task 进入终态后，旧定时器或异步回调不能把它重新激活。
6. 旧 Task 的回调不能推进后来提交的新 Task。
7. 执行期终止后，Plan 中保留的 `running` 只是冻结快照，不代表后台仍在执行。

不变量应在多个中间状态反复断言，而不是只在流程结束时看一次最终结果。

## Race Condition 与异步测试

Race Condition（竞态条件）是多个异步事件的结果取决于不受控的先后顺序。定时器、重复提交、组件卸载和终态切换都可能产生竞态。

异步测试应使用 Fake Timers（虚拟计时器）控制时间：

1. 建立明确初始状态。
2. 只推进到下一个边界，例如 500 ms 或 1000 ms。
3. 在每个边界断言 Task、Plan、Steps 和计时器数量。
4. 制造交错：旧 Task 等待 500 ms 时提交新 Task，再让旧回调到点。
5. 进入终态后继续推进足够长时间，确认状态没有复活。
6. 卸载组件后确认计时器被清理。

不要用真实等待验证定时行为。真实时间让测试变慢、易抖动，也难以精确复现事件顺序。

## Regression 与验证顺序

Regression（回归）是新修改破坏了原本正确的行为。高效顺序是：

```text
Targeted Tests（目标测试）
  ↓ 快速确认当前规则
Full Test Suite（完整测试集）
  ↓ 检查关联行为是否回归
Type Check + Production Build
  ↓ 检查静态与生产集成
Diff Review
  ↓ 检查范围、依赖和意外变化
```

目标测试通过只说明当前切片有进展；完整测试通过才能增加“没有破坏已知行为”的信心，但仍不能替代规格和 Diff 审查。

## 测试敏感性

Test Sensitivity（测试敏感性）指测试能否在规则真的被破坏时可靠失败。

可以做一次受控的反向检查：临时允许两个 `running`、移除终态保护，或让旧 Task 回调作用于新 Task；对应测试应该变红。随后恢复代码并重新运行验证。

如果故意破坏关键规则后测试仍然通过，说明测试可能只覆盖代码行、断言过宽，或根本没有触达风险点。敏感性比用例数量更重要。

## AI 修改测试时的警戒原则

当 AI 同时修改实现和测试时，风险会显著增加。测试可以因规格变化或覆盖缺口而修改，但不能为了绿灯降低规格。

需要警惕：

- 把精确断言改成宽泛的 `contains` 或只断言“存在”。
- 删除失败、取消、竞态或清理用例。
- 把原本期望的正确行为改成当前错误实现的结果。
- 跳过、隔离或静默吞掉失败测试。
- 用更新快照替代对行为变化的解释。

正确顺序是：先确认规格是否改变，再审查测试是否仍能证明验收标准，最后才看它是否为绿色。没有规格授权，绿色不能靠降低标准获得。

## 日常验证检查清单

- [ ] 每条验收标准是否有明确验证方法？
- [ ] 验证矩阵中是否存在空白或证据过弱的 Verification Gap？
- [ ] 是否同时覆盖 Happy Path、Failure Path 和关键 Invariant？
- [ ] 异步测试是否控制时间并断言中间状态、终态和清理？
- [ ] 是否验证旧回调不会重新激活终态或污染新 Task？
- [ ] 测试是否关注行为，而不是不必要的实现细节？
- [ ] 故意破坏关键规则时，相关测试是否会失败？
- [ ] AI 是否修改了测试；修改是否有规格依据，是否降低了断言强度？
- [ ] 是否先跑目标测试，再跑完整测试、类型检查和生产构建？
- [ ] 是否人工检查了真实行为、控制台和必要文案？
- [ ] 是否审查 Diff、依赖、锁文件和范围外变化？
- [ ] 最终报告的是实际证据，而不是“应该没问题”的声明？

## 1 分钟复习

1. 验证驱动开发是在实现前设计完成证据。
2. Claim ≠ Evidence；AI 的“已完成”不是证据。
3. 保持“规格 → 验收标准 → 验证方法 → 证据 → 完成”的可追溯链。
4. 用 Verification Matrix 找到 Verification Gap。
5. 静态、自动化测试、构建和人工验证各有能力边界，必须组合使用。
6. 优先测试行为，同时覆盖 Happy Path、Failure Path 和 Invariant。
7. 异步流程要控制时间、制造竞态，并证明终态不会被旧回调重新激活。
8. 先跑目标测试，再跑完整测试，防止 Regression。
9. 故意破坏规则时测试应该失败；否则测试不够敏感。
10. AI 可以补强测试，不能为了绿灯修改或降低规格。
