# 规格驱动开发（Spec-driven Development）

## 一句话理解

规格驱动开发不是先让 AI 写代码，而是先明确“要做对什么”，再用验收标准、测试和实现逐层证明它被正确完成。

```text
Intent（意图）
  ↓ 为什么做
Spec（规格）
  ↓ 做成什么样才算正确
Acceptance Criteria（验收标准）
  ↓ 哪些可观察结果能证明正确
Tests（测试）
  ↓ 自动检查这些结果
Implementation（实现）
  ↓ 用代码满足检查
```

代码生成越快，方向错误的实现也会越快扩散。规格的价值不是增加文档，而是把关键产品决策从 AI 的猜测中拿回来。

## Intent、Spec 与 Implementation 的区别

### Intent（意图）：为什么做

Intent 描述用户问题、业务价值和目标，不规定具体文件或技术写法。

本项目示例：

> 用户等待研究结果时，需要先知道系统准备从哪些方向展开研究。

### Spec（规格）：做成什么样

Spec 把目标变成明确的产品行为、状态变化、边界和完成条件。

本项目示例：

> 创建有效 Research Task 后先进入 `planning`；Mock Research Plan 生成成功后 Task 才进入 `researching`，并按顺序串行执行 3 个步骤。

### Implementation（实现）：具体怎么做

Implementation 是代码、文件和技术选择，例如 TypeScript 类型、Vue 模板、定时器和测试。它应服从 Spec，而不是反过来把偶然实现当成产品规则。

判断方法：

- “用户为什么需要它？”通常属于 Intent。
- “何时触发、怎样变化、什么算成功？”通常属于 Spec。
- “用哪个函数、组件或数据结构实现？”通常属于 Implementation。

## Spec 的七个要素

一个小功能的规格不必很长，但至少应回答七类问题。

### 1. 目标（Goal）

解决谁的什么问题，期望产生什么价值。目标不等于功能列表。

### 2. 触发条件与前置条件（Trigger and Preconditions）

什么事件启动功能，开始前必须满足什么条件。例如：规范化后的 Research Question 非空时才能创建 Task 与 Plan。

### 3. 输入、输出与领域模型（Input, Output, Domain Model）

输入和输出有哪些字段，字段含义是什么，哪些概念必须分开。例如 `ResearchTaskStatus` 与 `ResearchStepStatus` 是两种生命周期，不能复用同一类型。

### 4. 业务规则（Business Rules）

系统始终必须遵守的约束。例如 Plan 有 3–6 个完整 Steps，步骤串行执行，同一时刻最多一个 `running`。

### 5. 状态变化与异常路径（State Transitions and Failure Paths）

合法状态如何转换，哪些是终态，失败或取消后保留什么数据。未决定的异常传播规则不能由实现偷偷补全。

### 6. 验收标准（Acceptance Criteria）

用用户可观察或程序可验证的结果描述“完成”。每一条都应足够明确，能够转成测试或人工检查。

### 7. Non-goals（非目标）

明确当前版本不做什么。例如不重新生成 Plan、不做历史切换、不编辑或拖拽步骤、不显示虚假百分比、不接真实 AI API。

Non-goals 不是“以后永远不做”，而是“本轮没有足够证据支持，现在不做”。

## Scope Creep 与延迟决策

Scope Creep（范围膨胀）是功能在没有明确授权和验证需要时不断增加。AI 很容易根据常见产品模式主动补上历史版本、重试、暂停、进度条、数据库和抽象层；这些内容看起来完整，却会扩大 Change Surface（变更面）并引入新的产品假设。

控制范围的办法：

- 每个新增字段都追问：哪条规格或验收标准需要它？
- 每个新状态都追问：触发条件、退出条件和失败传播规则是否已确定？
- 每个新依赖都追问：现有技术是否真的无法完成当前切片？
- 把“可能以后需要”写入 Future Scope（未来范围）或 Decision Log（决策记录），不要提前写进代码。

延迟决策不是逃避决策，而是在证据出现前避免不可逆或高成本承诺。可以安全延迟的例子包括 Step 失败后是否跳过后续步骤、是否允许重新规划、是否需要持久化。当前必须决定的则包括 Plan 何时生成、Task 何时离开 `planning`、Step 是否串行，以及终态是否继续推进。

## 从规格到实现的可追溯链

推荐保持下面的单向关系：

```text
规格规则
“Plan 有 3–6 个完整 Steps”
        ↓
验收标准
“创建 Task 后可观察到 3–6 个含 id/title/description/status 的 Steps”
        ↓
自动化测试
检查数量、字段非空、id 唯一、初始状态为 pending
        ↓
实现
固定 Mock 模板与 createMockResearchPlan
```

如果测试无法对应任何验收标准，它可能只是在固定实现细节。如果验收标准没有测试或人工验证方式，它很容易变成无人检查的愿望。如果实现出现规格未提及的产品行为，应先判断它是必要实现细节还是隐藏决策；隐藏决策必须回到 Spec。

## 测试是高质量上下文

测试不只是最后的质量门，也是 AI 下一轮工作的高质量 Context（上下文）。好的测试能够告诉 AI：

- 哪些行为已经被确认，不能随意改变。
- 边界条件和合法状态转换是什么。
- 失败、取消和清理定时器时必须保持什么结果。
- 哪些命名与数据形状是项目契约。

测试质量取决于它是否验证产品行为。只检查函数被调用、组件存在或快照没有变化，提供的上下文较弱；检查用户可见结果、领域不变量和状态顺序，提供的上下文更强。

本项目用 fake timers（虚拟计时器）验证每秒状态推进，不进行真实等待。这既让测试快速稳定，也精确记录了时间相关规格。

## Spec Compliance

Spec Compliance（规格符合性）检查不是问“测试绿了吗”，而是逐条问：

1. 每条验收标准是否有自动化测试或明确的人工验证？
2. 测试是否真的验证该行为，而不是只覆盖代码行？
3. 实现是否加入了规格未授权的功能、状态、字段或依赖？
4. UI 是否暗示不存在的真实能力或虚假精确度？
5. 文档、测试、实现和当前 Git Diff 是否一致？
6. 类型检查、测试、生产构建和差异检查是否全部通过？

可以建立一张简单映射表：

| 规格 | 验收标准 | 测试 | 实现 |
| --- | --- | --- | --- |
| Plan 生成成功后开始研究 | `planning` 时尚无 Plan；成功后进入 `researching` | 提交后检查无 Plan，推进后检查 Plan 与首个 `running` Step | `advanceMockResearchTask` |
| Steps 串行执行 | 同时最多一个 `running` | 用虚拟计时器逐步检查状态 | `advanceMockResearchTask` |
| 不展示虚假进度 | 页面没有百分比和 progressbar | UI 非目标测试 | `App.vue` |

## 人主导与 AI 可委托的决策边界

人应主导高影响、难撤销或涉及真实用户价值的决策：

- 产品目标、用户和优先级。
- 范围、Non-goals 和成功标准。
- 状态机含义、失败传播和数据保留规则。
- 安全、隐私、成本与外部系统边界。
- 多个合理方案之间的产品取舍。

AI 可以在边界清楚时负责可验证、可逆的执行决策：

- 根据既有技术栈选择最小代码组织方式。
- 把验收标准转成测试用例。
- 实现明确的类型、转换函数和 UI 展示。
- 运行验证、检查命名、寻找规格与实现差异。
- 提出备选方案和风险，但不把建议伪装成已确认事实。

实用判断：如果一个决定会改变用户体验、数据契约、状态语义、范围或长期架构，AI 应先暴露它；如果它只是局部、可逆并能由现有测试验证，通常可以委托。

## 1 分钟复习

1. Intent 解释为什么做，Spec 定义做成什么样，Implementation 决定具体怎么做。
2. Spec 七要素：目标、触发与前置、输入输出与模型、业务规则、状态与异常、验收标准、Non-goals。
3. AI 会快速放大模糊需求；先把隐式产品决策变成显式规格。
4. 用 Non-goals 防止 Scope Creep；把没有证据的未来能力延迟决策。
5. 保持“规格 → 验收标准 → 测试 → 实现”的可追溯链。
6. 测试既是验证，也是向未来 AI 提供稳定行为契约的高质量上下文。
7. Spec Compliance 必须同时检查文档、测试、实现、UI、依赖和 Git Diff。
8. 人主导价值、范围和高影响取舍；AI 执行边界明确、可逆、可验证的工作。
