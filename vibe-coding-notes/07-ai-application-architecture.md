# AI 应用架构设计（AI Application Architecture）

## 一句话理解

AI 应用架构的核心，不是把项目提前拆成很多目录，而是把“用户交互、领域规则、业务协调、Agent 执行和外部副作用”放在清楚的边界内，使每一部分能够独立理解、替换和验证。

对 Deep Research Agent 来说，架构要回答的不是“应该有多少层”，而是：

> 谁接收研究目标，谁制定计划，谁执行步骤，谁调用外部工具，谁维护任务状态，谁判断结果是否足以继续。

当前项目仍处于单一 Research Task（研究任务）的前端本地 Mock（模拟）阶段。现有定时推进只验证任务、计划和步骤的生命周期，不等于已经实现真实搜索、核验、反思或报告生成。

## 普通应用与 Agent 应用的区别

普通应用的主流程通常由人和程序预先确定。用户触发一个操作，系统按照固定业务规则读取或修改数据：

```text
用户操作 → 页面 → 业务服务 → 数据或外部接口 → 确定结果
```

Agent（智能体）应用围绕目标组织工作。用户给出的通常不是一条完全确定的操作指令，而是一个需要规划、执行、观察和调整的目标：

```text
研究目标 → 制定计划 → 执行动作 → 观察结果 → 调整下一步 → 形成结果
```

| 对比维度 | 普通应用 | Agent 应用 |
| --- | --- | --- |
| 核心驱动 | 预定义操作和业务流程 | 目标与当前运行状态 |
| 路径 | 通常较固定 | 可能根据观察结果动态变化 |
| 输出 | 主要由确定性规则产生 | 可能包含模型生成的不确定结果 |
| 运行时间 | 多为短请求或短交互 | 可能跨多个步骤、工具调用和重试 |
| 失败方式 | 校验失败、接口失败、数据冲突 | 还包括计划不合理、工具结果不足、幻觉、循环失控和证据不足 |
| 验证重点 | 输入、规则与最终结果 | 还要验证过程、证据、停止条件和每次决策 |

二者并不是互斥关系。Agent 应用仍需要普通应用的表单、状态管理、权限、数据和错误处理；差别在于它还多了一条“根据目标决定下一步”的执行控制链。

## Agent Loop：智能体循环

Agent Loop（智能体循环）是一种持续根据目标和新证据选择下一步的控制过程：

```text
Goal（目标）
  ↓
Plan（计划）
  ↓
Act（行动）
  ↓
Observe（观察）
  ↓
Reflect（反思）
  ↓
Next Action（下一步）
  └──────────────→ 再次行动或停止
```

### Goal：目标

Goal（目标）描述最终希望达成的结果和约束，而不只是一次函数调用。

Deep Research Agent 的目标不是“调用搜索接口”，而是：围绕用户问题生成一份结论有证据、引用可追溯，并能表达不确定性的研究报告。

### Plan：计划

Plan（计划）把目标拆成可执行、可观察的 Research Steps（研究步骤）。计划应包含研究范围、步骤顺序、预期产物和必要的停止条件。

计划不是永远正确的剧本。真实 Agent 在证据不足、来源冲突或工具失败时，可能需要补充或调整计划；当前项目明确不实现重新规划。

### Act：行动

Act（行动）是执行当前步骤，例如搜索、读取网页、提取证据、比较来源或生成报告草稿。行动会产生副作用、成本和错误，因此必须经过明确的 Tool 权限边界。

### Observe：观察

Observe（观察）是把行动结果转换成可供系统判断的结构化事实，例如：找到哪些 Source（来源）、提取了哪些 Evidence（证据）、工具是否失败、还缺少哪个研究维度。

观察不是简单保存一段模型文本。系统需要知道结果来自哪里、是否完整、能否支持某个结论。

### Reflect：反思

Reflect（反思）是比较当前观察与目标：证据是否足够，来源是否冲突，计划是否仍有效，是否应该重试、补充搜索、换工具或停止。

反思必须受规则限制。没有最大步数、成本预算、超时和停止条件的“不断反思”，很容易演变成无限循环。

### Next Action：下一步

Next Action（下一步）是基于反思得到的受控决策：执行某个计划步骤、重新规划、请求人工确认、生成报告，或者以完成、失败、取消等状态结束。

关键认识：Agent Loop 不是“调用一次大模型并返回答案”，也不是必须让模型决定一切。确定性规则负责状态不变量和安全边界，模型只在需要语义判断的受控位置参与决策。

## Deep Research Agent 中的对应关系

当前项目已经具备 Agent Loop 的外形，但只实现了确定性的前端 Mock 生命周期：

| Agent Loop 概念 | 当前项目中的对应 | 当前限制 |
| --- | --- | --- |
| Goal | 用户输入的 `question`，被创建为 `ResearchTask` | 只保存问题，没有真实目标澄清和质量约束 |
| Plan | `createMockResearchPlan` 创建的固定三步 `ResearchPlan` | 不是 LLM 动态规划，也不能重新规划 |
| Act | `MockResearchRunner` 定时调用 `advanceMockResearchTask` 推进 Step | 没有执行搜索、阅读、核验或报告生成 |
| Observe | 页面收到新的 `ResearchTask` 快照，并展示 Task、Plan、Step 与错误状态 | 观察对象只是 Mock 状态，不是真实工具结果和证据 |
| Reflect | 当前没有实现 | 不判断证据充分性、来源冲突或计划质量 |
| Next Action | `advanceMockResearchTask` 根据固定状态规则决定下一个 Step 或终态 | 是预定义状态机，不是根据研究结果动态决策 |

因此，当前项目可以准确描述为：

> 已建立单一 Research Task 的领域状态、业务协调边界和可替换 Runner 契约，并用本地 Mock 验证串行执行生命周期；尚未实现真实 Agent Loop。

这个区分非常重要。架构图表达未来方向，不能被当成当前能力清单。

## 四层职责划分

当前 `apps/web/src` 已经形成四个可识别的职责层，而不需要为了形式立刻创建四套目录。这里的 Runner（运行器）指承载一次研究运行的执行实现。

```text
前端层 App.vue
  ↓ 调用
业务服务层 research-task-service.ts
  ↓ 依赖执行契约
Agent 执行层 mock-research-runner.ts
  ↓ 使用领域规则
领域模型层 research-task.ts
```

状态更新沿相反方向返回页面；依赖方向和数据流方向不必完全相同。

### 前端层

前端层负责用户可观察的交互和展示：

- 绑定 Research Question 输入；
- 决定按钮是否可用；
- 调用业务服务开始研究；
- 保存最新的页面响应式快照；
- 展示 Task、Plan、Step、错误和 Mock 说明；
- 页面卸载时触发资源释放。

前端层不应维护合法状态转换表，不应解析 Mock 标记，也不应直接持有 LLM（大语言模型）API Key（接口密钥）、调用搜索工具或实现重试策略。

### 领域模型层

领域模型层负责表达业务事实和保护不变量：

- `ResearchTask`、`ResearchPlan`、`ResearchStep` 和结构化错误；
- Task 与 Step 各自独立的状态类型；
- 合法状态转换和终态不可继续推进；
- 进入 `researching` 时 Plan 必须匹配且恰有一个运行中 Step；
- 进入 `generating` 前所有 Steps 必须完成。

领域规则应尽量保持为不依赖 Vue、网络、模型 SDK（软件开发工具包）和计时器的纯逻辑。当前 `research-task.ts` 还暂时包含固定 Mock Plan 和 Mock 推进函数；在真实执行能力出现前，这种小规模混合可以接受，不必为了“看起来分层”提前搬目录。

### 业务服务层

业务服务层负责一个用例如何被协调，而不是负责页面渲染或具体工具实现。当前 `ResearchTaskService`：

- 判断规范化问题能否开始；
- 启动新的 Research Run（研究运行）；
- 停止旧运行；
- 用运行版本阻止旧回调覆盖新任务；
- 在页面销毁时统一释放资源。

未来它可以协调创建、取消、重试和恢复，但只有对应产品行为出现后才增加这些职责。

### Agent 执行层

Agent 执行层负责“如何完成研究运行”。当前 `MockResearchRunner`：

- 解析仅用于开发和测试的 Mock 标记；
- 用计时器推进固定流程；
- 模拟 planning 或 researching 阶段的失败和取消；
- 在终态、停止或替换运行后停止后续推进。

未来真实 Runner 可以在同一业务边界后面协调 Planner、Executor 和 Tools。页面不需要知道当前使用 Mock Runner 还是真实 Runner，这就是边界带来的可替换性。

## Planner、Executor、Tool 与 Memory

Planner（计划器）、Executor（执行器）、Tool（工具）和 Memory（记忆）是 Agent 执行层内部常见角色，不等于必须创建四个类或四个目录。

| 角色 | 核心职责 | 不应承担的职责 | 当前项目状态 |
| --- | --- | --- | --- |
| Planner（计划器） | 把目标转成结构化、可验证的 Research Plan | 直接操作页面、偷偷执行工具、绕过计划结构 | 固定 Mock 模板仅模拟最小计划产物 |
| Executor（执行器） | 按计划选择并执行 Step，处理取消、超时和执行事件 | 自行修改领域不变量、无限重试、把工具文本直接当事实 | Mock Runner 只模拟串行推进 |
| Tool（工具） | 封装搜索、网页读取、内容提取或模型调用等受控能力 | 决定整个任务目标、直接改写 Task、隐藏来源和错误 | 尚未实现任何真实 Tool |
| Memory（记忆） | 保存本次运行需要的上下文、观察、来源、证据和决策记录 | 成为无边界的数据堆、自动等同于向量数据库 | 只有页面内存中的 Task 快照，不是持久化 Agent Memory |

四者的关系可以概括为：

```text
Goal → Planner → Plan → Executor → Tool
                         ↓         ↓
                      状态事件 ← Observation
                         ↓
                       Memory
                         ↓
                  下一步或停止判断
```

### 对 Memory 的克制理解

Memory 不等于一开始就引入向量数据库。至少要区分：

- Working Memory（工作记忆）：当前运行正在使用的计划、步骤、观察和中间结果；
- Execution History（执行历史）：为了审计和恢复而保存的动作、工具结果和状态事件；
- Long-term Memory（长期记忆）：跨任务复用的稳定信息。

当前阶段只有刷新即可丢失的页面内存状态。只有当“恢复长任务”“查看历史”或“跨任务复用信息”成为明确需求时，才设计持久化 Memory。

## 单一职责原则

Single Responsibility Principle（单一职责原则）不是“每个文件只能有一个函数”，而是：

> 一个模块应该只有一种主要的变化原因。

在当前项目中：

- 页面文案或布局变化，主要影响 `App.vue` 和样式；
- Task 合法转换变化，主要影响 `research-task.ts`；
- 新旧运行替换和资源释放策略变化，主要影响 `research-task-service.ts`；
- Mock 时间线或终态模拟变化，主要影响 `mock-research-runner.ts`。

判断职责是否需要拆分时，应问“这些代码是否因为不同原因、以不同节奏变化”，而不是只看文件行数。小文件也可能混合职责，大文件也可能仍在表达一个完整而内聚的概念。

## God Component：上帝组件问题

God Component（上帝组件）是同时承担页面渲染、领域规则、业务协调、异步执行和外部调用的超大组件。

如果所有逻辑都继续堆进 `App.vue`，它可能同时负责：

- 读取和校验问题；
- 创建 Task 和 Plan；
- 维护全部状态转换；
- 注册和清理计时器；
- 调用 LLM 与搜索接口；
- 处理重试、取消、来源和证据；
- 渲染所有页面状态。

后果不是单纯“代码很长”，而是：

- 领域规则只能通过 UI 间接测试；
- 计时器、网络和响应式状态相互干扰；
- 替换 Mock 执行为真实执行时必须重写页面；
- 迟到回调、重复提交和卸载清理更容易出错；
- AI 修改一个功能时很难控制 Change Surface（变更范围）。

当前项目把状态规则、运行协调和 Mock Runner 从 `App.vue` 中分离，已经减少了上帝组件风险。是否继续拆展示组件，应由独立展示职责或复用需求触发，而不是由“组件超过某个行数”自动触发。

## 为什么 AI 项目特别需要边界设计

### 1. 模型输出具有不确定性

LLM 的文本不能直接被当作合法领域对象。Planner 的输出需要结构化验证，Executor 也不能绕过状态转换直接改写 Task。

### 2. 外部内容是不可信输入

搜索结果和网页内容可能错误、恶意或包含 Prompt Injection（提示词注入）。Tool 只能返回受控数据，外部文本不能获得系统权限或直接决定下一步动作。

### 3. Agent 运行更长且异步事件更多

长任务会遇到取消、超时、迟到结果、重复提交和页面卸载。当前服务的运行版本保护与 Runner 的 `stop` 边界，就是这种问题的最小预演。

### 4. 每次行动可能产生真实成本和副作用

模型 Token（计量单元）、搜索配额、写文件、发消息或调用业务 API 都可能产生成本或不可逆影响。规划与执行分离后，系统才能在 Tool 边界实施权限、预算和人工确认。

### 5. 供应商和能力会快速变化

页面与领域模型不应依赖某个模型 SDK 的返回格式。稳定的业务契约包住易变的 Provider（服务提供方）细节，才能低风险替换模型、搜索源或执行策略。

### 6. 结果质量必须可追溯

最终报告不只要“读起来合理”，还要能从 Claim（论点）追溯到 Evidence（证据）和 Source（来源）。没有清楚的数据边界，引用很容易退化成模型生成的装饰。

## Evolutionary Architecture：演进式架构

Evolutionary Architecture（演进式架构）是在保持关键边界和可验证性的前提下，让架构随真实需求逐步生长。

它不是“先随便写，以后重构”，也不是“第一天设计最终形态”，而是：

1. 先保护当前已经确认的不变量；
2. 在最可能变化的位置建立最小契约；
3. 每次只加入一个可独立验证的能力；
4. 用测试、评测和运行证据决定下一次演进；
5. 只有职责真实出现时才创建对应抽象和目录。

当前项目的 `ResearchRunner` 契约就是一个合适的演进缝隙：业务服务只关心如何规范化问题、启动运行、接收 Task 更新和停止运行；Mock 细节被隔离在 Runner 后面。未来接入真实执行时可以替换实现，但不能假设所有真实 Agent 需求已经被当前接口覆盖。

演进式架构关注的是可逆决策。文件如何分目录通常容易调整；Task 状态语义、引用可追溯性、安全权限和外部 API 契约更难修改，应优先明确。

## 延迟设计：不提前实现未来复杂能力

延迟设计不是拒绝思考未来，而是记录方向和触发条件，同时暂不支付实现成本。

当前阶段不应仅为了“架构完整”提前加入：

- 空的 `domain/`、`services/`、`agent/` 或 `tools/` 目录；
- 没有第二种实现的复杂工厂和依赖注入框架；
- 尚无恢复需求的数据库、任务队列和分布式状态机；
- 尚无跨任务需求的向量数据库和长期 Memory；
- 尚未验证单 Agent 流程的 Multi-Agent（多智能体）编排；
- 没有真实风险模型支撑的通用权限系统。

更好的方式是为未来能力写下“何时引入”的触发条件：

| 真实信号 | 再考虑的设计 |
| --- | --- |
| Source、Evidence、Report 已开始独立演化 | 拆分领域文件或 `domain/` 目录 |
| 出现真实 Runner 或多个 Agent 执行模块 | 建立 `agent/` 目录并并存 Mock/真实实现 |
| 长任务必须跨刷新恢复 | 持久化、任务队列和执行历史 |
| 同类 Tool 超过一个且有共同协议 | 提取 Tool 接口、权限和错误模型 |
| 单 Agent 经评测成为明确瓶颈 | 再评估 Multi-Agent 是否值得 |

原则是：

> 先为今天的真实复杂度建立清晰边界，再为已经出现的变化提取抽象。

## 架构评审问题清单

### 目标与范围

- [ ] 这张架构图描述的是当前事实，还是未来方向？是否明确标注？
- [ ] 当前切片解决了什么用户问题？Non-goals（非目标）是什么？
- [ ] 是否把 Mock、原型或占位能力误写成真实 Agent 能力？

### 职责与依赖

- [ ] 每一层的输入、输出和主要变化原因是否清楚？
- [ ] 页面是否只负责交互与展示，而不是维护领域状态机？
- [ ] 领域模型是否独立于 Vue、计时器、网络和模型 SDK？
- [ ] 业务服务是否协调用例，而没有吞并具体 Tool 实现？
- [ ] Agent 执行是否通过明确契约向外报告状态和错误？

### Agent Loop 与数据

- [ ] Goal、Plan、Action、Observation 和停止条件分别由谁管理？
- [ ] Planner 输出是否结构化并经过边界验证？
- [ ] Tool 结果是否保留来源、错误和可信度信息？
- [ ] Claim 是否能追溯到 Evidence，Evidence 是否能追溯到 Source？
- [ ] Memory 保存什么、保留多久、由谁读取，是否真的需要持久化？

### 运行与安全

- [ ] 取消、超时、重试、重复提交和迟到事件如何处理？
- [ ] 终态是否保证不再推进？资源是否能统一释放？
- [ ] Tool 的权限、预算、副作用和人工确认边界是否明确？
- [ ] API Key 是否被隔离在受控服务端，而不是浏览器页面？
- [ ] 外部网页和模型输出是否始终按不可信输入处理？

### 演进与验证

- [ ] 能否用更小、可逆的切片验证同一个假设？

## 当前项目架构演进路线

### 阶段 0：当前状态——验证生命周期

```text
Vue 页面
→ ResearchTaskService
→ MockResearchRunner
→ ResearchTask / Plan / Step 状态规则
```

目标是验证单一 Task、固定 Plan、串行 Steps、失败、取消、资源释放和迟到事件保护。当前不调用真实 LLM、搜索、数据库或后端。

### 阶段 1：补全可追溯研究数据

按 Product Spec 逐个实现 Source、Evidence、Report 和 Citation（引用）的领域模型、不变量、Mock 展示与测试。先证明“证据和引用如何关联”，再接真实搜索。

### 阶段 2：引入真实 Planner

在受控服务边界接入一次真实计划生成，把模型输出验证为结构化 `ResearchPlan`。页面和 Task 生命周期继续依赖稳定契约，执行步骤仍可保持 Mock，以隔离规划质量与执行复杂度。

### 阶段 3：引入单一串行 Executor 与最小 Tool

一次只接入一种只读 Tool，例如搜索或网页读取；Executor 串行执行 Steps，保存真实 Source 和 Evidence，并明确超时、取消、错误和预算。先验证端到端最小路径，不做并行和 Multi-Agent。

### 阶段 4：形成受控 Agent Loop

增加结构化 Observation、证据充分性判断、有限重试和明确停止条件。Reflect 只能在步数、成本、时间和权限预算内决定下一步，所有决定留下可观察记录。

### 阶段 5：按真实需求增加恢复与评测

只有长任务跨刷新恢复、任务历史或后台执行成为产品要求时，才引入持久化、队列和执行历史。单 Agent 流程经过固定研究 Case 的质量、成本和延迟评测后，再判断是否需要 Multi-Agent。

每次演进都遵循：

```text
更新 Spec
→ 明确边界和不变量
→ 实现一个最小切片
→ 自动化测试与 Eval（评测）
→ Review Diff
→ 决定下一步
```

## 一分钟复习

1. 普通应用执行预定义操作；Agent 应用围绕目标循环决定下一步。
2. Agent Loop 是 `Goal → Plan → Act → Observe → Reflect → Next Action`，必须有停止条件。
3. 当前 Deep Research Agent 只有固定 Mock 生命周期，不是真实 Agent Loop。
4. 前端负责交互，领域层保护不变量，业务服务协调用例，Agent 执行层完成运行。
5. Planner 制定计划，Executor 执行步骤，Tool 封装外部能力，Memory 保存必要上下文和记录。
6. 单一职责关注“变化原因”，不是文件大小或目录数量。
7. 上帝组件的危险是职责耦合、难测试和难替换，不只是代码很长。
8. AI 输出不确定、外部内容不可信、运行时间长且工具有副作用，因此边界尤其重要。
9. 演进式架构先保护稳定不变量，再根据真实变化提取抽象。
10. 延迟设计是记录方向与触发条件，不提前实现不存在的复杂能力。
11. 当前优先补全 Source、Evidence、Report 和 Citation，再逐步接入真实 Planner 与 Executor。
12. 架构是否合理，最终要由可替换性、可追溯性、安全性和验证证据证明。
